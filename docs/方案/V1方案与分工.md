# 脚印 V1 · 五人小组分工与路演方案

> 版本：v1.0  
> 范围：自带搭子的双人学习监督产品  
> 交付：一次可现场演示的路演  
> 团队：5 人

---

## 1. 项目目标

V1 只验证一件事：**两个已经认识的人，愿不愿意用「脚印」互相监督学习，并持续打卡。**

### 1.1 完整演示主线

```
注册 → 生成/输入邀请码 → 直接绑定 → 解锁功能
→ 设置目标 → 打卡 → 查看积分/愿望单 → 解绑 → 历史数据保留
```

### 1.2 明确不做

- 搭子发现、推荐、搜索
- 公开广场、排行榜
- 站内聊天
- 手机号/邮箱注册
- 通知推送
- 多人关系
- 小程序/App

### 1.3 路演要讲的一句话

> 我们不是再做一个打卡工具，而是让「一个人学不下去」变成「有一个人和你一起学」。

## 2. 五人角色分工

| 成员 | 角色 | 主要职责 | 最终交付物 |
|---|---|---|---|
| 成员 1 | 项目负责人 / 产品 & 路演 | 锁定需求范围、页面流程、验收标准；写路演主线、讲稿、Q&A；协调进度和分工 | V1 需求文档、验收清单、路演 PPT、讲稿、Q&A 手册 |
| 成员 2 | 后端 A / 账号与配对 | 注册、登录、登出、改密、恢复码；邀请码生成/输入/绑定；`pairs` 关系表 | 账号与配对 API、接口文档、单元测试 |
| 成员 3 | 后端 B / 数据与权限 | 数据库迁移、`pair_id` 隔离、权限校验、种子数据、隔离测试 | 迁移脚本、权限中间件、隔离测试报告 |
| 成员 4 | 前端 A / 主流程 | 登录/注册页、配对页、未配对锁定态、路由守卫、像素 UI 一致性 | 认证与配对页面、锁定态页面、可点击流程 |
| 成员 5 | 前端 B / 功能适配 & 交付 | 配对后原有页面适配、部署、演示账号、备份视频、端到端测试、路演素材 | 可运行演示环境、演示数据、备份视频、截图素材 |

### 分工原则

- **不按页面分，按接口和模块分**：避免前后端互相等待。
- **每个人都有一个明确的最终交付物**：不是「参与开发」，而是「交出什么」。
- **负责人只有 1 个**：每个工作包只有一个 owner，其他人配合。

## 4. 接口契约（先定死，前后端并行）

### 4.1 账号

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/register` | 昵称 + 密码注册，返回恢复码 |
| POST | `/api/login` | 昵称 + 密码登录 |
| POST | `/api/logout` | 登出 |
| GET | `/api/me` | 当前用户 |
| POST | `/api/me/password` | 修改密码 |
| POST | `/api/me/recover` | 用恢复码重置密码 |

### 4.2 配对

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/pair/invite` | 生成邀请码（6 位，24 小时有效） |
| GET | `/api/pair/invite` | 查看我当前的邀请码和状态 |
| POST | `/api/pair/join` | 输入邀请码，直接绑定 |
| GET | `/api/pair/current` | 当前搭子信息、绑定时间 |
| POST | `/api/pair/unbind` | 解绑；历史数据保留 |

### 4.3 原有接口

`/api/goals`、`/api/checkins`、`/api/wish`、`/api/partner`、`/api/stats` 全部保留，但所有查询必须带当前 `pair_id`。

### 4.4 统一返回格式

```json
{
  "ok": true,
  "data": {},
  "error": null
}
```

错误时：

```json
{
  "ok": false,
  "data": null,
  "error": { "code": "PAIR_NOT_FOUND", "message": "还没有绑定搭子" }
}
```

## 5. 数据模型要点

### 5.1 新增表

```sql
CREATE TABLE pairs (
  id SERIAL PRIMARY KEY,
  user_a_id INTEGER NOT NULL,
  user_b_id INTEGER NOT NULL,
  status TEXT NOT NULL DEFAULT 'active', -- active | ended
  created_at TEXT NOT NULL,
  ended_at TEXT,
  ended_by INTEGER
);

CREATE TABLE pair_invites (
  id SERIAL PRIMARY KEY,
  code TEXT NOT NULL UNIQUE,
  creator_id INTEGER NOT NULL,
  status TEXT NOT NULL DEFAULT 'pending', -- pending | used | expired
  expires_at TEXT NOT NULL,
  created_at TEXT NOT NULL
);
```

### 5.2 修改表

```sql
ALTER TABLE goals ADD COLUMN pair_id INTEGER;
ALTER TABLE check_ins ADD COLUMN pair_id INTEGER;
ALTER TABLE verifications ADD COLUMN pair_id INTEGER;
```

### 5.3 关键规则

- 一个用户同一时间只能有一个 `active` pair
- 邀请码 6 位、24 小时有效、只能使用一次
- 解绑后 `pairs.status = 'ended'`，历史数据保留
- 解绑后双方仍可查看历史数据，但不能新增/修改
- 新绑定关系只能看到新 `pair_id` 下的数据
- 第三个用户永远不能访问其他 pair 的任何数据

## 6. 路演脚本（6 分钟版）

### 0:00–0:50 痛点

> 「早上 7:50，图书馆三楼，她一个人到了。她不是不想学，她只是知道，今天大概率又会刷一上午手机。她试过打卡 App、番茄钟、学习群，但都没有用——因为没有人真的看见她。」

### 0:50–1:30 洞察

> 「一个人学习最难的不是不会，是没人看见。打卡工具解决的是记录，我们解决的是关系。」

### 1:30–2:10 方案

> 「脚印是一个双人学习监督空间。你和你的搭子绑定之后，可以一起设目标、打卡、看到彼此的进度、用积分兑换奖励。第一版我们不做陌生人匹配，因为关系质量比匹配数量更重要。」

### 2:10–4:40 现场演示

1. 注册账号 A（昵称 + 密码）
2. 生成邀请码
3. 注册账号 B，输入邀请码
4. 直接绑定成功，功能解锁
5. A 设置一个「今天背 50 个单词」的目标并打卡
6. 切到 B，看到 A 的进度，点一次「拍一拍」
7. 展示积分变化、连续天数、愿望单
8. 解绑，展示历史数据仍然保留

### 4:40–5:30 价值与差异

- 不是单人打卡，是双人关系
- 不是靠意志力，是靠「被看见」
- 不是复杂社交，是低压力陪伴
- 先做关系，再做匹配：留存验证后再开放发现层

### 5:30–6:00 未来

> 「当双人关系被验证后，我们会把匹配层打开：按目标、作息、地点找到同频的人。脚印先让两个人学下去，再让更多人找到彼此。」

## 8. 演示环境与素材

### 必须准备

- 两个测试账号：`demo_a` / `demo_b`
- 邀请码提前生成好一个，避免现场网络问题
- 预置一周打卡记录，展示连续天数和积分
- 演示用浏览器两个窗口并排，或两台设备
- 一段 2 分钟录屏作为备份
- 路演 PPT 一份（PDF 备份）
- 一页纸项目介绍（含二维码/链接）

### 演示禁忌

- 不现场注册全新账号（网络/验证码风险）
- 不演示边缘功能
- 不在答辩前改代码
- 不临时换演示数据

## 9. 常见评委问题与回答

### Q1：为什么第一版不做搭子匹配？

> 因为匹配不是最难的，关系留存才是。我们先把两个人能不能坚持验证清楚，再去做匹配。否则匹配来的人也会流失，是漏水的桶。

### Q2：这和普通打卡 App 有什么区别？

> 普通打卡是记录自己，我们是让另一个人看见你。打卡只是动作，关系才是留存的原因。

### Q3：用户为什么不用微信互相监督？

> 微信太吵，消息会淹没，也没有结构。脚印把目标、打卡、进度、积分、兑换放在一个安静的空间里，关系更轻，但更持续。

### Q4：怎么冷启动？

> 第一版不做陌生人匹配，用户自带搭子——同学、室友、考研搭子都可以。等双人留存跑通，再开放匹配池。

### Q5：怎么赚钱？

> 第一版不考虑商业化。后续可以面向学校、考研机构、自习室做团体版，或者提供高级统计和小组功能。

### Q6：数据隐私怎么保证？

> 每个用户只能看到自己当前搭子的数据；第三个人无法访问任何目标、打卡和证据图片。解绑后历史数据只读保留。

### Q7：为什么保留像素风？

> 它让产品不像又一个效率工具，更像一个有温度的小世界。学习已经够苦了，我们希望它轻一点。

## 10. 协作规则

- **唯一事实来源**：需求以 `V1方案与分工.md` 为准，接口以本文档第 4 节为准
- **每日同步 10 分钟**：昨天做了什么、今天做什么、卡在哪
- **分支规范**：`feat/auth`、`feat/pair`、`feat/data-scope`、`feat/ui`
- **合并规则**：每个 PR 至少一个人 review，不直接推 main
- **周五冻结**：周五下午之后不再改功能代码，只修 bug
- **路演前 24 小时**：代码冻结，录制备份视频
