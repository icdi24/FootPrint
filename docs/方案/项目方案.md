# 脚印 · 学习搭子平台 — 项目方案 v0.1（讨论稿）

> 日期：2026-11-07  
> 状态：讨论中，待拍板  
> 技术底座：GitHub `icdi24/FootPrint`（现有的双人监督打卡 + 积分系统）

---

## 0. 一页结论

- **产品定位**：给有明确学习目标、每天独自自习的大学生，按「目标 / 作息 / 地点」匹配同频学习搭子，并用双人契约、轻量打卡和可见进度，把陪伴坚持到考试结束。
- **和 FootPrint 的关系**：FootPrint 是「已经认识的两个人的监督执行系统」，我们保留它的目标、打卡、积分、愿望单内核；在它前面补「发现与匹配」，在后面补「关系生命周期」。
- **MVP 范围**：1v1 搭子 + 7 天试搭 + 双人目标打卡 + 阶段目标互验 + 个人奖励清单 + 简单站内消息；不做群组、不做公开社区、不做音视频、不做 AI 匹配。
- **试点方式**：先单校 50–100 人，人工匹配跑通，再上线规则匹配。
- **最关键的验证指标**：7 天试搭存活率、周打卡完成率、4 周留存。

## 1. 用户洞察（先把「我觉得」换成「他真的」）

| 问题 | 我们的回答 |
|---|---|
| **谁在用** | 有明确考试节点、每天固定自习、但一个人坚持困难的大学生。优先：考研 / 考公 / 考证 / 期末冲刺。不是「所有想学习的人」。 |
| **什么场景** | 早上到图书馆、下午犯困、晚上回宿舍复盘；想找人一起自习，但不想尬聊、不想被放鸽子。 |
| **卡在哪** | 找不到同频的人（目标、作息、地点、强度四个条件难同时满足）；打卡没人看见；搭子三天就散；陌生人社交有安全顾虑。 |
| **现在怎么凑合** | 微信群/QQ群喊人、小红书发帖找搭子、番茄 ToDo/Forest 自己计时、室友互相叫、付费自习室。 |
| **现有解法的不足** | 群聊信息流太吵、匹配靠运气；打卡工具没有关系约束；熟人监督怕欠人情；陌生人缺少信任与退出机制。 |

### 一句话用户场景

> 「明天早上 8 点，我想在图书馆三楼从高数开始学。我知道一个人也能去，但我知道自己大概率会赖床、会刷手机。我希望有个同样考数一的人已经在那个位置，不用聊天，互相看一眼进度就行。」

## 2. 产品定位与原则

### 2.1 定位

**脚印 · 学习搭子**：一个有始有终的学习关系平台。

不是泛社交，不是学习资料库，也不是单纯打卡工具。它解决的是「从想学，到坐下来学，再到明天继续学」的全过程。

### 2.2 五条产品原则

1. **关系先于功能**：匹配不是终点，关系能持续才是。
2. **轻社交**：不鼓励无限刷人、不鼓励闲聊；一切互动围绕学习任务。
3. **可见即可信**：双方进度默认可见，不靠繁琐的打卡验证。
4. **有始有终**：试搭、续约、毕业、退出，每一步都有明确规则。
5. **安全优先**：不暴露精确位置和联系方式，举报/拉黑随时可用。

### 3.1 L1 发现层

#### 学习档案（注册后 1 分钟内填完）

MVP 只收 8 个字段，避免注册流失：

| 字段 | 类型 | 说明 |
|---|---|---|
| 目标类型 | 单选 | 考研 / 考公 / 考证 / 期末 / 语言 / 技能 / 其他 |
| 具体目标 | 文本 ≤ 50 字 | 如「26 考研数一」「雅思 6.5」 |
| 考试/截止日期 | 日期 | 可留空 |
| 每周学习天数 | 1–7 | |
| 每日可投入时长 | 分钟 | |
| 常去地点 | 单选 + 文本 | 本校图书馆 / 自习室 / 宿舍 / 线上 |
| 学习时段 | 多选 | 早（6–9）/ 上午（9–12）/ 下午（14–18）/ 晚上（18–23） |
| 监督强度 | 1–3 | 1=轻提醒，2=每天互相报进度，3=强监督（可催、可要求证据） |

可选补充：学校/城市、年级、是否接受异性搭子、个人介绍（≤100 字）。MVP 先不做性别筛选，避免把产品做成交友软件；如确有需要，放到 P1。

#### 匹配规则（MVP 用规则，不用 AI）

**硬条件（不满足不推荐）：**

- 目标类型相同
- 每周至少 3 个学习时段重叠
- 同校/同城，或双方都接受线上

**软条件（加权评分）：**

| 条件 | 权重 |
|---|---|
| 具体目标相似（关键词/考试科目） | 25 |
| 考试日期相差 ≤ 30 天 | 15 |
| 每日投入时长相近（±60 分钟） | 15 |
| 学习地点相同/相近 | 15 |
| 监督强度相同 | 10 |
| 补充资料完整度 | 5 |

**推荐策略：**

- 每人每天最多看 3 个候选，避免无限刷人和比较心理
- 每张卡片给出「匹配理由」，例如：「都在准备 26 考研」「都在图书馆三楼」「都习惯早上 8 点开始」
- 双方都点「想认识」才进入试搭；一方拒绝不通知对方具体原因

#### 试搭（7 天）

匹配成功不等于成为正式搭子，先进入 7 天试搭期：

| 阶段 | 要完成的事 |
|---|---|
| 第 1 天 | 系统给出 3 个破冰问题（不用尬聊）：互相介绍目标、约定本周学习时段、说一条自己的雷区 |
| 第 2–6 天 | 每天各自打卡；可以看到对方是否完成；可以「拍一拍」提醒 |
| 第 7 天 | 双方各做一个 3 题复盘：节奏合不合、是否继续、愿不愿意推荐给朋友 |

- 双方都选「继续」→ 转为正式搭子
- 任一方选「不继续」→ 体面结束，系统发送模板消息，不显示对方拒绝理由
- 48 小时无响应 → 试搭自动结束

### 3.2 L2 关系层（复用 FootPrint）

#### 保留的核心

| FootPrint 能力 | 在学习平台里的用法 |
|---|---|
| 日常目标 | 每日学习目标：背单词、刷题、写论文、复习一章 |
| 阶段目标 | 学习里程碑：模考 6.5、写完初稿、刷完 1000 题 |
| 打卡 | 长按完成、可选证据、10 秒内结束 |
| 阶段目标验收 | 必须对方通过，避免「自己说完成就完成」 |
| 积分 | 学习积分，记录投入和坚持 |
| 连续里程碑 | 3/7/14/30 天奖励，给正反馈 |
| 周视图 | 保留，一眼看到本周打卡格子 |
| 统计 | 学习时长、完成率、连续天数，两人并排不排名 |
| 数据备份 | 保留，平台化后作为用户数据导出能力 |

#### 需要改造的

| 原设计 | 问题 | 新方案 |
|---|---|---|
| 固定两个账号 | 无法注册、无法多用户 | 改成正常注册/登录，平台支持多用户 |
| `partnerOf` = 数据库里另一个用户 | 第三个用户会串号 | 新建 `pairs` 关系表，按当前 active pair 取搭档 |
| 目标只属于用户 | 换搭子后旧目标会被新搭子看到 | 目标增加 `pair_id`，按关系隔离 |
| 愿望单是「商品 + 事件」 | 陌生人之间「让对方代劳/请客」很怪 | MVP 先做「个人奖励清单」：自己给自己定奖励（奶茶、看剧、游戏时间），积分自己兑；搭子间的「小约定」放 P1 |
| 没有消息 | 匹配后无法沟通 | 加最简单的站内文字消息；MVP 不做图片和语音 |
| 没有通知 | 用户不会主动回来 | 先做站内红点和每日 21:00 汇总，P1 接微信服务号 |

#### 关系内的具体规则

- **每人同时只能有 1 个正式搭子**（MVP 约束，降低关系复杂度）
- 目标默认对搭子可见；证据图片只有双方可见
- 日常目标自评即入账；阶段目标必须对方验收
- 对方可以「拍一拍」提醒，但不能代替打卡
- 对方可以驳回明显造假的打卡，需填理由
- 积分只增不减；断卡只影响「本可以得到的分」和连续记录，不扣已有余额
- 任何一方可以随时结束关系，历史记录保留

### 3.3 L3 生命周期层

#### 周复盘

每周日 20:00 自动生成一张「本周学习卡」：

- 本周打卡 X/Y 天
- 总学习时长
- 最长连续
- 搭档对比（不排名）
- 一句系统建议 + 一句可复制发给对方的话

#### 关系状态机

```
陌生人
  ↓ 浏览/推荐
候选搭子
  ↓ 双方「想认识」
试搭中（7 天）
  ↓ 双方确认继续          ↓ 任一方不继续 / 超时
正式搭子（active）        已结束（ended）
  ↓ 考试结束 / 任一方退出
已结营（graduated）
```

#### 换搭与结营

- **失联处理**：对方连续 3 天无打卡且无回应 → 系统提示「是否重新匹配」
- **换搭**：结束当前关系后可立即重新匹配；历史数据保留
- **结营**：考试结束后可生成「结营报告」：一起坚持了几天、累计多少小时、互相见证了什么
- **不惩罚退出**：不公开差评、不显示「被抛弃次数」，避免羞辱和报复

## 4. 核心用户流程

### 4.1 新用户首次进入

```
登录/注册 → 填学习档案（1 分钟）→ 看今日推荐 3 人 → 发出「想认识」
→ 对方同意 → 进入 7 天试搭 → 第 7 天双方决定 → 正式搭子
```

### 4.2 日常使用

```
打开首页 → 看到今日目标和搭子状态 → 长按「完成」打卡（10 秒）
→ 看搭子是否也完成 → 可拍一拍 → 晚上看本周格子
```

### 4.3 关系结束

```
考试结束 / 节奏不合 / 对方失联 → 发起结束（可选原因）
→ 生成结营小结 → 可重新匹配
```

### P1（试点后）

- 自动匹配评分优化（权重可调）
- 周报/月报
- 微信服务号提醒
- 搭子间「小约定」：占座、带饭、请奶茶等（从 FootPrint 事件类愿望单改造）
- 校园认证（学生证/校园邮箱）
- 管理员后台：用户管理、举报处理、人工配对

### P2（验证后再做）

- 3–5 人学习小组
- 线上自习室/连麦
- AI 学习总结/匹配
- 学习足迹地图、年度报告
- 校园大使/组织者角色

### 明确不做

- 公开动态广场、排行榜、颜值社交
- 付费课程、资料交易
- 音视频直播
- 陌生人直接交换联系方式（试搭期不允许）
- 复杂惩罚、押金、现金对赌

## 6. 技术方案

### 6.1 现有底座盘点

| 层 | 现状 | 处理方式 |
|---|---|---|
| 后端 | Node.js 22 + Express + PostgreSQL | 保留 |
| 前端 | 原生 HTML/CSS/JS，无构建步骤 | 保留，新增页面按现有模式写 |
| 账号 | 初始化时固定创建 2 个账号 | 重写为注册/登录 |
| 搭档 | `SELECT * FROM users WHERE id != ? LIMIT 1` | 替换为 `pairs` 关系表 |
| 目标/打卡/积分 | 完整可用 | 保留，增加 `pair_id` |
| 愿望单 | 商品 + 事件，偏情侣/熟人 | 改名为「奖励」，MVP 先做个人奖励 |
| 统计/周视图 | 完整可用 | 保留 |
| 备份导出 | 完整可用 | 保留 |
| 视觉 | 温馨 16-bit 像素风 | 保留，作为品牌差异 |

### 6.2 改造原则

1. **不推倒重写**：先加表、加字段、加页面，保持原有功能随时可回退。
2. **一次只改一层**：先账号/关系，再发现/试搭，最后奖励/运营。
3. **所有查询强制带 `pair_id`**：防止换搭后数据串号。
4. **新页面用现有设计语言**：继续使用像素字体、硬边框、暖色系，不另起一套 UI。

### 6.6 安全与权限

- 所有 `goals` / `check_ins` / `verifications` 查询必须校验当前用户属于该 `pair`
- 证据图片仅本人和当前搭子可见，URL 不可猜
- 精确位置只到「校区/图书馆」，不存宿舍号
- 试搭期不提供手机号/微信交换入口
- 举报后 24 小时内管理员可见；被举报用户不能继续发消息
- 登录失败限流、会话 30 天、密码 bcrypt
- 上线前补：隐私政策、用户协议、未成年人提示

## 7. MVP 里程碑

| 阶段 | 时间 | 交付 | 验收标准 |
|---|---|---|---|
| M1 基础改造 | 第 1–2 周 | 多用户注册登录、学习档案、`pairs` 表、人工配对、双人主页 | 两个新用户可注册、填写档案、被管理员配对、看到对方 |
| M2 关系闭环 | 第 3–4 周 | 目标/打卡/积分/统计接入 pair、个人奖励 | 配对后能设目标、打卡、对方可见、积分正常 |
| M3 发现与试搭 | 第 5–6 周 | 推荐列表、匹配申请、7 天试搭、站内消息、举报拉黑 | 用户可自主完成「浏览→申请→试搭→转正」全流程 |

## 8. 试点与验证

### 8.1 试点设计

- **范围**：一所学校 / 一个校区，50–100 名用户
- **招募**：考研群、自习室社群、校园墙
- **前两周人工匹配**：运营在后台根据档案手动配对，验证需求真伪
- **后两周开放自动推荐**：对比人工 vs 自动的匹配质量

### 8.2 核心指标

| 指标 | 定义 | 目标 |
|---|---|---|
| 建档完成率 | 注册后完成 8 项档案 / 注册人数 | ≥ 60% |
| 匹配成功率 | 7 天内形成试搭 / 完成档案人数 | ≥ 40% |
| 试搭存活率 | 7 天后双方选择继续 / 试搭对数 | ≥ 50% |
| 周打卡完成率 | 实际打卡次数 / 应打卡次数 | ≥ 60% |
| 4 周留存 | 第 4 周仍在使用 / 首周活跃 | ≥ 30% |
| 主观有效 | 「有人陪更容易坚持」选择同意 | ≥ 80% |

### 8.3 停止/调整条件

- 试搭存活率 < 30%：先修匹配和试搭流程，不继续加功能
- 建档完成率 < 40%：档案字段太多或引导有问题，先减法
- 周打卡完成率 < 40%：说明打卡机制不成立，回到用户访谈

## 9. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 单校用户密度不够，匹配不到人 | 产品看起来「空的」 | 先单校试点；人工匹配兜底；候选不足时显示「等待同频的人」而不是空列表 |
| 陌生人社交安全 | 骚扰、隐私泄露 | 试搭期不交换联系方式；举报/拉黑；位置只到校区；管理员审核 |
| 搭子关系脆弱，几天就散 | 留存差 | 7 天试搭 + 结构化破冰 + 周复盘 + 失联重配 |
| 积分/愿望单对陌生人很怪 | 用户不理解 | MVP 只做个人奖励；搭子间小约定放 P1 |
| 多租户改造引入串号 | 隐私事故 | 所有查询强制 `pair_id`；写自动化测试覆盖「第三个人看不到」 |
| 考试结束流失 | 生命周期短 | 结营报告、毕业后转为轻量学习记录、下学期重新匹配 |
| 范围膨胀 | 做不完 | 明确不做清单；每周对 MVP 范围 |

## 10. 需要一起拍板的事

1. **首批试点学校/人群**：哪所学校、哪个考试群体？这决定匹配池。
2. **1v1 还是小组**：我建议 MVP 只做 1v1；小组会显著增加关系复杂度。
3. **奖励机制**：接受「个人奖励清单」先行，还是必须保留 FootPrint 的「搭子间愿望单」？
4. **聊天范围**：站内文字消息够不够？还是希望匹配后直接加微信？（我建议试搭期只用站内）
5. **视觉风格**：继续 FootPrint 的像素风，还是改成更「学习工具」的清爽风？像素风有辨识度，但可能显得游戏化。
6. **品牌名**：继续叫「脚印」，还是换一个更直接的名字（如「同频」「搭个学」）？
